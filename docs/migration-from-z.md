# 既存 ℤ(api.php)からの移行

方針: **api.php を止めずに並行稼働**し、ユーザーが自分のタイミングで移る。

## 段階

1. **リレーを追加**(`/msg` `/sse` `/media` `/x/handle` `/.well-known/macaron.json`)。新しい SQLite `events` を別ファイルで用意。api.php はそのまま。
2. **エクスポートAPIを足す**(`api.php?a=export`、ログイン必須): 自分のプロフィール・投稿・返信・引用・リポスト・いいね・リアクション・フォロー・ブックマーク・カスタム絵文字を JSON で返す。
3. **移行画面**(ログイン済みで開く): クライアントが鍵を作り、下の手順でイベントを署名して送る。
4. 移行済みユーザーが増えたら、アプリの既定を Macaron 側にする。api.php は**読み取り互換の薄い層**(events から旧JSONを組み立てる)に縮める。
5. 旧書き込みAPIを止める。

## 移行画面の処理

```
1. 鍵を生成して、バックアップを保存させる(これを済ませるまで先へ進めない)
2. プロフィール kind 10000 を作成(avatar / banner / deco / badges を絶対URLに)
3. ハンドルを取得: POST /x/handle  — このとき旧セッションで本人確認し、旧ハンドル → 新pubkey を結ぶ
4. 自分の投稿を id 昇順で処理:
     イベントを作る(created_at は元の時刻のまま)
     parent_id → 親の「新イベントid」に置換して e/p タグ
     quote_id  → 同様に q/p タグ
     本文の #タグ → t タグ、@handle → p タグ(相手が移行済みなら。未移行はそのまま文字)
     :name: → emoji タグ(旧 emojis 表のURL)
     media → imeta タグ(URL・w・h・sha256)
     sensitive=1 → cw タグ
     署名して EVENT、旧id→新イベントid の対応を保存
5. 自分のフォロー・リポスト・いいね・リアクション・ブックマーク:
     対象の投稿 / ユーザーが移行済みなら通常どおり作る
     未移行なら「保留リスト」に入れ、相手が移行したら再開(対応表 legacy_map を使う)
6. カスタム絵文字を kind 30000 として公開
7. 終了。旧アカウントに「移行済み」表示
```

### 対応表 `legacy_map`

サーバー側に `(旧post_id, 新イベントid, 新pubkey)` を持ち、**移行済みの人の投稿を参照する側**がこれを引いて `e` タグを作る。旧ユーザー ↔ 新pubkey は `.well-known/macaron.json` と同じ表。

## 移行しないもの

| もの | 理由 |
|---|---|
| DM | 暗号化できる鍵が相手側に無い(相手も移行してから)。希望者には平文をファイルで渡す |
| 通知・既読位置・閲覧履歴 | 派生データ。`notif_read` を現在時刻で初期化する |
| コミュニティ認定のセンシティブ | 投稿者本人の `cw` のみ引き継ぐ。他人のフラグは再度付けてもらう |
| `terms` `trend_cache` `ogp_cache` | キャッシュ |
| パスワード | 持ち越さない(鍵がパスワードの代わり) |

## 時刻の扱い

過去の `created_at` で送るので、リレーは**過去側を制限してはいけない**(未来側だけ `created_at_window` を見る。[08-relay](../core/08-relay.md))。

## メディア

- 旧 `uploads/m/…` `uploads/e/…` のURLは**そのまま使える**ようにしておく(絶対URL化して `imeta` に入れる)。
- 新規アップロードから `POST /media`(内容ハッシュ名)に切り替え。古いファイルの `x`(sha256)は移行時に計算して埋める。

## リスク

- **鍵の紛失**を前提に、バックアップ画面の導線を強く作る(QR・ファイル・パスフレーズ付き書き出し)。
- 移行途中に旧APIへ投稿が続くと差分が出る → 移行画面を開いた時点で**旧側を読み取り専用**にして、最後に差分を再エクスポート。
- 本人以外が「移行」を完了させないこと(旧セッションで認証してからのみ)。
