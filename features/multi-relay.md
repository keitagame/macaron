# 機能: 複数リレー・分散

- 使う kind: [10001 リレーリスト](../kinds/10001-relay-list.md)
- 現行: 単一サーバー(`api.php`)のみ。**この機能は新規**で、無くても動く(1リレー運用)

## 段階

| 段階 | 構成 | 必要なもの |
|---|---|---|
| 0 | リレー1台 = 現行と同じ運用 | なし |
| 1 | クライアントが複数リレーに投稿・取得 | 設定(リレーURL一覧) |
| 2 | 他人のリレーを自動で探す(アウトボックス) | kind 10001・[handle](handle.md) の `relays` |
| 3 | リレー同士の同期(ミラー) | リレー間の `REQ` を使うだけ(特別な仕様なし) |

## 書く

自分の `write` リレー全部に同じ署名済みイベントを `EVENT`。1つ成功すれば成功とみなす(失敗分は後で再送)。

## 読む(アウトボックス方式)

1. フォロー中の人ごとに、その人の kind 10001 から `write` リレーを調べる(分からなければ[handle](handle.md)の `relays`、それも無ければ自分の既定リレー)。
2. リレーごとにまとめて、そのリレーに書いている人たちの投稿を `REQ`。
3. 受け取ったイベントは**署名を検証**し、`id` で重複を除く。
4. 自分宛て(メンション・通知・DM)は自分の `read` リレーを購読。

## 事実と注意

- 署名があるので、**どのリレーから受け取っても内容は同じ**に信頼できる(改ざんされたら署名が合わない)。リレーを信用する必要がない。
- 削除([kind 5](../kinds/5-deletion.md))は**リレー単位**。全リレーに送るが、保存し続けるリレーもある。
- 件数([counts](counts.md))は**リレーごとに違う**。表示は「このリレーで見える数」。
- `since`/`until` での取りこぼしは、複数リレーなら補い合える。
- `created_at` は端末の時刻を使う。リレーは**未来側に15分以上ずれたもの**を拒否する([08-relay](../core/08-relay.md))ので、端末の時計は合わせておく(過去の時刻は許可されるので、移行やミラーで古いイベントを送れる)。

## ミラー(リレー同士の同期)

リレーAがリレーBに、通常のクライアントとして `REQ {"since":…}` を張り、受け取ったイベントを自分の DB に保存するだけ。署名で検証済みなので信用の仕組みは増えない。ミラー元・ミラーするkind・対象のpubkeyは運営者が決める。

## 引っ越し

アカウント = 鍵なので、**リレーを変えてもアカウントは変わらない**。新しいリレーを kind 10001 に書き、過去の自分のイベントを新リレーに `EVENT` で再送(署名はそのまま通る)。[docs/migration-from-z](../docs/migration-from-z.md)。

## 拡張ポイント

- リレーの「発見」は kind 10001 を集めた一覧、または運営者の手動リストで十分。専用の仕組みは後から。
